# REIE DXT Wave 1C Buyer Seller Shared Hierarchy Foundation Implementation Plan

Program: REIE Decision Experience Transformation (DXT 1.0)

Phase: Wave 1C - Buyer Seller Shared Hierarchy Foundation Implementation Plan

Status: `REIE_DXT_WAVE_1C_BUYER_SELLER_SHARED_HIERARCHY_FOUNDATION_PLAN_COMPLETE_LOCAL_ONLY`

Date: August 2, 2026

## 1. Executive Implementation Decision

Selected foundation model:

`DOCUMENTATION_AND_DETERMINISTIC_CONTRACT_ONLY`

The first Wave 1C implementation should establish a shared hierarchy contract and a focused deterministic validation check before any Buyer or Seller runtime page is changed. This creates consistency without forcing premature shared components, data schemas, or page abstractions.

Runtime implementation is not authorized by this plan.

## 2. Foundation Purpose

The shared foundation should give Buyer and Seller pages the same decision architecture while preserving their different customer problems.

Shared foundation sequence:

1. page orientation;
2. governing decision question;
3. concise opening promise;
4. preparation themes;
5. tool or evidence continuation;
6. questions to verify;
7. professional and trust boundaries;
8. advisory transition;
9. compact next-decision continuations.

The foundation should reduce drift, reduce density, and make later Buyer and Seller phases easier to certify independently.

## 5. Selected Foundation Model

`DOCUMENTATION_AND_DETERMINISTIC_CONTRACT_ONLY`

Implementation should create:

- one authoritative hierarchy contract;
- one focused deterministic check;
- no shared runtime component;
- no Buyer runtime edit;
- no Seller runtime edit;
- no route, API, persistence, CRM, telemetry, provider, or data change.

The contract should be consumed by future Buyer and Seller implementation charters and certification checks.

## 6. Mandatory Hierarchy Roles

Mandatory roles:

- page orientation;
- governing decision question;
- concise opening promise;
- preparation themes;
- tool or evidence continuation;
- questions to verify;
- professional and trust boundaries;
- advisory transition;
- compact next-decision continuations.

Every future Buyer/Seller section must clearly map to one role.

## 7. Optional Hierarchy Roles

Optional roles:

- eyebrow label;
- supporting heading;
- brief evidence link;
- secondary continuation;
- compact disclosure;
- related journey link;
- lower research continuation.

Optional roles may appear only when they clarify the decision. They must not create a dense manual, card wall, or equal-weight CTA cluster.

## 8. Buyer-Specific Requirements

Buyer-specific content must preserve:

- readiness orientation;
- financing assumptions;
- Search continuation;
- property verification;
- offer and transaction preparation;
- Buyer Financing Planner boundaries;
- Advisory transition.

The Buyer page must not imply qualification, approval, affordability, buying power, lender recommendation, rate recommendation, loan recommendation, or underwriting.

## 9. Seller-Specific Requirements

Seller-specific content must preserve:

- property preparation;
- evidence gaps;
- pricing-context boundaries;
- market exposure preparation;
- buyer-objection preparation;
- offer and transaction preparation;
- Advisory transition.

The Seller page must not imply valuation certainty, price recommendation, guaranteed buyer behavior, seller net sheet, legal conclusion, title conclusion, condition conclusion, or disclosure sufficiency.

## 10. Shared CTA Contract

CTA rules:

- one primary CTA per stage;
- at most one subordinate secondary CTA when necessary;
- no equal-weight CTA clusters;
- Advisory appears after preparation;
- destinations must use existing routes;
- CTAs must be verb-led and understandable;
- no scheduling, qualification, upload, provider, CRM, telemetry, or hidden context-transfer behavior.

## 11. Progressive Disclosure Contract

Progression:

1. first viewport: one question, one promise, one dominant action;
2. immediate post-intent: preparation themes;
3. stage-level detail: only enough guidance to support the next decision;
4. tool or destination detail: planner, Search, evidence, or market route when relevant;
5. trust/professional boundary: adjacent to the related decision area;
6. lower continuation: compact routes for continued research.

Never show simultaneously:

- all tools;
- all routes;
- dense disclosure walls;
- multiple primary CTAs;
- scoring or readiness labels;
- broad educational article content above the customer’s governing question.

## 12. Desktop Contract

Desktop behavior:

- editorial rhythm;
- restrained content width;
- clear directional headings;
- limited complementary two-column layouts;
- no dashboard, portal, scorecard, or intake-product appearance;
- meaningful whitespace without disconnected empty regions.

## 13. Tablet Contract

Tablet behavior:

- readable line lengths;
- staged content blocks;
- clear CTA order;
- compact continuation groups;
- no crowded multi-column card wall;
- no overflow or clipped CTAs.

## 14. Mobile Contract

At approximately `390x844`:

- one opening question;
- one dominant opening action;
- short stage units;
- clear separation;
- maximum two visible actions per major viewport;
- stable touch targets;
- no dense card grid;
- no disclosure wall;
- no horizontal overflow.

Mobile is not a compressed desktop layout. It should read as a single decision narrative.

## 15. Accessibility Contract

Future implementation must preserve:

- semantic heading order;
- logical reading order;
- keyboard-operable links;
- visible focus behavior;
- accessible disclosure controls;
- stable touch targets;
- sufficient contrast;
- no color-only meaning;
- reduced-motion compatibility where relevant;
- no hidden essential guidance.

## 16. Financing Boundary

Buyer Financing Planner boundaries remain controlling:

- user-entered assumptions only;
- educational arithmetic only;
- no provider;
- no persistence;
- no qualification;
- no approval;
- no affordability or buying-power conclusion;
- no lender, rate, or loan recommendation.

## 17. Valuation Boundary

Seller journey must not create:

- valuation certainty;
- price recommendation;
- investment projection;
- seller net sheet;
- guaranteed market outcome;
- buyer-behavior prediction;
- tax, legal, insurance, or condition advice.

## 18. Evidence Boundary

Property / Seller Evidence may organize known facts and gaps. It must not determine:

- legal status;
- ownership;
- title;
- permits;
- zoning;
- HOA obligations;
- condition;
- environmental risk;
- insurance eligibility;
- disclosure sufficiency;
- suitability;
- valuation certainty.

## 19. Fair-Housing And Professional Boundaries

Do not introduce:

- demographic targeting;
- protected-class proxies;
- family-status steering;
- school rankings;
- safety or crime rankings;
- socioeconomic comparisons;
- desirability claims;
- "best" or "ideal for" language;
- suitability conclusions;
- scoring;
- grades;
- progress percentages;
- approval or qualification language.

Professional verification remains required for financing, title, legal, tax, insurance, HOA, zoning, permit, condition, valuation, and disclosure matters.

## 20. Implementation Sequencing

Recommended sequence:

1. Shared hierarchy foundation implementation.
2. Buyer Journey Simplification.
3. Seller Journey Simplification.

Foundation should be documentation/check-only unless a later authorization proves that page-local checks cannot maintain consistency.

Stop conditions preventing premature abstraction:

- repeated runtime structure has not yet been proven on both pages;
- a shared component would force identical Buyer and Seller content;
- a schema would require route, data, or persistence changes;
- implementation would touch Buyer/Seller runtime before the foundation gate;
- certification cannot isolate file scope.

## 22. Acceptance Criteria

Future foundation implementation passes when:

- one shared hierarchy contract exists;
- Buyer and Seller remain content-specific;
- heading and CTA roles are consistent;
- density-reduction rules are explicit;
- mobile behavior is defined;
- accessibility contract is enforceable;
- financing, valuation, evidence, fair-housing, and professional boundaries remain intact;
- no premature design system or shared runtime component is introduced;
- no route, API, data, persistence, CRM, telemetry, provider, or brokerage-disclosure change occurs;
- deterministic validation is feasible;
- later Buyer and Seller implementations can be separately certified.

## 26. Stop Conditions

Stop future foundation implementation if:

- a runtime component is required to define the contract;
- Buyer/Seller runtime edits become necessary;
- route, API, persistence, CRM, telemetry, provider, or data changes become necessary;
- privacy, financing, valuation, evidence, fair-housing, or professional boundaries cannot be enforced;
- more than one foundation model remains equally recommended;
- deterministic validation cannot be scoped without touching runtime pages.
